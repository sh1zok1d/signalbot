# BTC Signal Bot — Product Spec v0

Источник: продуктовая спецификация пользователя (передана в рамках диагностики
Этапа 1, 2026-07-16). Это главный источник требований проекта — реализация
(включая Этап 1: data_ingestion + backfill + storage) должна проверяться на
соответствие этому документу, а не наоборот.

> **Поправка (2026-07-17) — MVP на 3 биржах.** После приёмки Этапа 1 владелец
> продукта отключил **Bitget** из активного MVP (тег `pre-disable-bitget` →
> `stage1-three-exchanges`). Активный набор: **Binance, Bybit, OKX**
> (`config.enabled_exchanges`). Данные и код Bitget сохранены; Bitget может быть
> включён позже по критериям из `docs/STAGE1_ACCEPTANCE.md §5`. Соответственно
> консенсус пересчитан на 3 биржи (см. «Жёсткие правила»).

## MVP

- Инструмент: **BTCUSDT**.
- Биржи (known): Binance, Bybit, OKX, Bitget. **Активные в MVP: Binance, Bybit,
  OKX** (Bitget отключён — см. поправку выше).
- Тип контракта: **USDT perpetual**.
- Базовая гранулярность метрик: **1m**.
- Подтверждение сигналов — на закрытии **5m**.
- Контекст (старшие таймфреймы): **15m, 1h, 4h**.
- Без автоматической торговли (только детекция/уведомление сигналов).

## Будущие события (signal_engine, не в этом этапе)

1. Long/short capitulation.
2. Level sweep and reclaim/rejection.
3. Position buildup без направления.
4. Accumulation/distribution breakout после подтверждения.

## Состояния сигнала

```
EARLY → ARMED → TRIGGERED → INVALIDATED/EXPIRED
```

## Жёсткие правила (hard gates)

- OI, funding и liquidations **сами по себе** не дают LONG/SHORT — это
  контекстные метрики, не самостоятельный сигнал направления.
- **TRIGGERED невозможен без ценового подтверждения.**
- Отсутствующие данные **нельзя заменять нулём** — отсутствие источника,
  отсутствие истории и реальный ноль должны быть различимы.
- Для консенсуса по price/OI/order flow требуется подтверждение нескольких
  бирж. **На 3-биржевом MVP** (поправка 2026-07-17): normal = **≥2 из 3**,
  strong = **3 из 3**, **1 из 3 запрещает сигнал**; `liquidations_min_sources = 2`
  (см. `config.yaml → consensus`). Исходное требование было «минимум 3 из 4».
- **Coverage** (сколько бирж сейчас доступно/валидны) должен отображаться
  отдельно от самих сигналов/метрик.
- Пороги (percentile-based) рассчитываются **позже**, на основе накопленной
  истории (percentile_engine, не этот этап).
- Высокий Setup Score **не отменяет** обязательные hard gates выше.

## Область этого этапа

Этап 1 (data_ingestion + backfill + storage) — только получение, сохранение и
валидация данных. **percentile_engine и signal_engine сознательно не
реализуются** до отдельного подтверждения этого этапа.
