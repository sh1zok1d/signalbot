## 2. Процедура прекращения платежей

1. Владелец заполняет недостающие поля таблицы §1 (провайдер VPS, облако для rclone, план GitHub, подписки) в приватной заметке вне git.
2. Порядок закрытия — обратный зависимости данных: сначала всё, что не хранит данные (5, 6, 7, 3-Actions), затем Telegram (4) после S7, затем VPS (1) после S8, последним — off-site хранилище (2) после переноса закрывающей копии на носители владельца.
3. Для каждого ресурса: выключить автопродление → экспортировать счета/историю платежей (для учёта) → отозвать ключи → удалить способ оплаты → закрыть аккаунт, если он нужен был только проекту.
4. Через 35 дней после закрытия — проверка выписок по карте: ни одного списания от ресурсов из §1.
5. Запись о выполнении — в `docs/closure/SHUTDOWN_LOG_<дата>.md` (без номеров счетов и сумм, только факт закрытия и дата).

## 3. Персональные данные участников

### 3.1. Что есть

По записям репозитория внешних пользователей у продукта не было (`docs/CURRENT_STATE.md:120`, `PROJECT_STATUS.md`; первая когорта `NOT_STARTED`; `access.preview_owner_only: true`). В базе могут быть строки владельца, тестовых аккаунтов и «известных контактов» (`docs/BETA_PREVIEW_V1.md:68-80` требует удалить тестовый аккаунт после проверки — проверить, сделано ли).

Где лежат персональные данные (`storage/beta_v0_schema.sql`, см. инвентарь):
- сырые идентификаторы Telegram: `beta_users` (`telegram_user_id`, `chat_id`, `tz`, `trader_type`, `brief_time`, `tier`, флаги push), `beta_allowlist`, `beta_waitlist`;
- связанные через `user_pk`: голоса `beta_feedback`, `beta_message_votes`; свободный текст `beta_feedback_messages`; причины `beta_reasons`; активность `beta_user_activity`; личные уровни `beta_price_alerts`; `beta_owner_forwards`; доставки `beta_notification_deliveries` (`telegram_message_id`, `error_summary`); `beta_market_alerts.target_user_pk`;
- псевдонимы: `beta_admin_audit` (HMAC-отпечатки с `BETA_FINGERPRINT_KEY`; старые строки — некейированный SHA-256, восстанавливаемый перебором), `beta_rejected_start_hashes` (HMAC с `BETA_TELEMETRY_SALT`), legacy `telegram_notification_deliveries.recipient_fingerprint` (некейированный SHA-256 chat id);
- вне базы: копии свободного текста участников в личном Telegram-чате владельца (`runtime/beta_bot.py:511-535`); все дампы базы (локальные 7, off-site 30/12/12) содержат персональные данные (`beta_v0_schema.sql:9-15`); **journald до 2026-09-28 мог содержать токен бота** (hotfix `53ccec14`; ротация токена после этого в записях не зафиксирована).

Обещания участникам (privacy notice v8, `beta/i18n.py:522-578`): хранение активности и текстов 120 дней; `/delete_me` удаляет всё; автоудаление через 30 дней после `/stop`; рыночные и прогнозные записи персональных данных не содержат. Purge-процедуры работают только внутри `--beta-notify-once` (`beta/delivery.py:307-319`): **после остановки таймеров автоматические удаления прекращаются**, поэтому закрытие должно выполнить их вручную.

### 3.2. Принцип

Закрытие не должно оставить участников в худшем положении, чем обещала privacy notice. Научная ценность продукта от персональных данных не зависит: ни одна таблица результатов (`beta_claims*`, `forecast_*`, `beta_forecasts`, `beta_episode_outcomes`, лента состояний, `beta_shadow_*`) не содержит идентификаторов пользователей. Поэтому по умолчанию персональные данные **удаляются**, а не архивируются.

### 3.3. Порядок (чек-лист S0–S7; необратимая часть — по разрешению П4)

Порядок жёсткий: приложение остановлено (S3), **PostgreSQL работает**; финальный полный зашифрованный дамп снят и проверен (S4); только потом обезличивание в живой базе (S6); затем повторный экспорт (S7); контейнеры останавливаются после всего (S8).

1. **Инвентаризация (S0):** `SELECT status, count(*) FROM beta_users GROUP BY status; SELECT count(*) FROM beta_allowlist; … beta_waitlist; … beta_feedback_messages; … beta_owner_forwards;` — счётчики без идентификаторов в `SHUTDOWN_LOG`.
2. **Уведомление (S1):** если среди `ACTIVE` есть кто-то, кроме владельца и тестовых аккаунтов, — финальное сообщение с указанием, что данные удаляются, и датой.
3. **Удаление в живой базе (S6, П4):** одна воспроизводимая процедура `scripts/closure/deidentify_closure.sql` (dry-run по умолчанию, `-v apply=1` для выполнения; одна транзакция). Она повторяет правило `delete_participant` (`storage/beta_v0_store.py:1207-1250`) для всех участников сразу: счётчик `beta_deleted_cohort_counts` (включая старые строки удаления по правилу OUT-8), `DELETE` из `beta_users` с каскадом, `beta_allowlist`, `beta_waitlist`; `beta_invites.label` → `redacted`; `beta_notification_deliveries.error_summary` → `redacted`; `telegram_notification_deliveries`/`telegram_notifier_state.recipient_fingerprint` → NULL; `beta_rejected_start_hashes` удаляется (`beta_rejected_start_counts` остаётся); каждый персональный отпечаток в `beta_admin_audit` (keyed и legacy, как строки) деидентифицируется через схемную `beta_audit_deidentify()` (отпечатки владельца → роль `owner`, остальные → `participant`); встроенная проверка откатывает транзакцию, если какая-либо таблица участников не пуста, в аудите остались отпечатки или детали, или изменился счётчик любой таблицы результатов. Протестирована на изолированной базе: `scripts/closure/test_deidentify_closure.sh` (результаты — `TEST_REPORT_2026-10-15.md`). После COMMIT — `VACUUM (FULL)` затронутых таблиц и `CHECKPOINT`.
4. **Обезличенный дамп (S7):** `closure_backup.sh --apply` повторно → `closure_backup_deid_<метка>` (всё зашифровано). Это долгосрочный архив. Полный дамп с персональными данными (`closure_backup_final_<метка>`), CSV участников, журналы и старые копии — по §3.5.
5. **Вне базы (S9):** владелец удаляет пересланные тексты участников из своего Telegram-чата с ботом (или чат целиком); journald на VPS уничтожается вместе с VPS; зашифрованный экспорт журналов хранится как часть полного архива (§3.5), так как может содержать старый токен; токен отзывается в S9 в любом случае.
6. **Ключи псевдонимизации:** `BETA_FINGERPRINT_KEY`, `BETA_TELEMETRY_SALT` лежат в `secrets.tar.gz.gpg` полного архива; уничтожаются вместе с ним по §3.5. Пока полный архив существует, ключи нужны для его проверки.
7. **Запросы участников после закрытия:** контакт владельца остаётся; при запросе — подтверждение удаления по `beta_deleted_cohort_counts` и дате `SHUTDOWN_LOG`; если полный архив ещё существует (§3.5) — удаление записи участника из него невозможно без расшифровки, поэтому ответ — дата запланированного уничтожения архива.

### 3.4. Что остаётся навсегда

Агрегаты без идентификаторов: `beta_deleted_cohort_counts`, `beta_rejected_start_counts`, даты действий в аудите (OUT-8), все рыночные и прогнозные таблицы, журнал заявок — всё в обезличенном архиве `closure_backup_deid_<метка>`.

### 3.5. Судьба копий с персональными данными и срок хранения

**Инвентарь копий, содержащих персональные данные в момент закрытия** (все, кроме п. 1, — в открытом виде):

| № | Копия | Где | Как создана |
|---|---|---|---|
| 1 | `closure_backup_final_<метка>` (полный дамп, CSV участников, журналы, секреты) | VPS → off-site → диск владельца | зашифрована этим планом |
| 2 | локальные дампы `/opt/signalbot/backups/*.sql.gz` (до 7) | VPS | `backup.sh`, не зашифрованы |
| 3 | off-site тиры `daily/` (до 30), `weekly/` (до 12), `monthly/` (до 12) | rclone-remote | `sync_backup_offsite.sh`, не зашифрованы |
| 4 | снапшоты/образы VPS у провайдера, если делались | провайдер | вручную |
| 5 | копии, которые владелец мог снимать на свой компьютер (`scp` дампов, `artifacts/`) | машины владельца | вручную |
| 6 | живая база на VPS до S6; volumes до уничтожения VPS. После обезличивания и `VACUUM FULL` строк нет в файлах таблиц, но они остаются в сегментах WAL до переиспользования (проверено тестом: `TEST_REPORT_2026-10-15.md`) | VPS | — |
| 6a | зашифрованная копия volumes (чек-лист S8) и снапшот VPS у провайдера (S10) — содержат WAL и остатки диска, то есть остаточные персональные данные; **не архив**, а кратковременная страховка на время уничтожения сервера | off-site / диск владельца / провайдер | этим планом |
| 7 | пересланные тексты участников в Telegram-чате владельца | Telegram | бот |

**Основания хранения.** Privacy notice v8 обещает участникам: активность и тексты — 120 дней, удаление через 30 дней после `/stop`, `/delete_me` — удаление всего. Договорных, платёжных и бухгалтерских оснований нет: платежи не собирались (`config/beta_v0.yaml:148-150`, U3 не запускался), внешних участников по записям не было, претензий и споров не зафиксировано. Если это так, **законного основания хранить полный архив с персональными данными после закрытия нет**, и срок хранения не нужен вовсе: полный архив (п. 1) уничтожается сразу после того, как обезличенный архив `closure_backup_deid` проверен восстановлением, а копии 2–7 — в порядке ниже. Срок не назначается «по умолчанию»; если владелец видит основание хранить (например, неурегулированный запрос участника, возврат платежа, если он всё же был, обязательство перед третьим лицом), он записывает в `SHUTDOWN_LOG` основание, срок и дату уничтожения, и этот срок не превышает того, что обещано participants (120 дней от последней активности).

**Процедура уничтожения (после подтверждения `closure_backup_deid` на двух копиях вне VPS):**

1. Копия 1: удалить зашифрованные файлы на всех носителях (`shred -u`/`rm` — для шифротекста достаточно обычного удаления, секрет — пароль); у облака — удалить и очистить корзину (`rclone delete`, затем `rclone cleanup <remote>:` для Google Drive или эквивалент); записать дату.
2. Копии 2 и 6: `shred -u /opt/signalbot/backups/*` (по возможности: на SSD/CoW/снапшотах не гарантирует уничтожения) и очистка journald в S7; volumes уничтожаются вместе с VPS (S10). Копия 6a: зашифрованная копия volumes удаляется со всех носителей, снапшот — в панели провайдера, оба сразу после подтверждения `closure_deid` на двух носителях; дата в `SHUTDOWN_LOG`.
3. Копия 3: `rclone lsl <remote>:<path>` — инвентарь с датами в `SHUTDOWN_LOG` (имена файлов, без содержимого); затем `rclone purge <remote>:<path>/daily`, `…/weekly`, `…/monthly` и `rclone cleanup`; оставить только `closure_final_*` (до п. 1) и `closure_deid_*` (бессрочно). Если off-site remote никогда не настраивался (на 2026-10-08 не подтверждён), записать «отсутствует».
4. Копия 4: удалить снапшоты в панели провайдера после S10 и подтверждения архива; провайдеры хранят удалённые снапшоты некоторое время — записать дату.
5. Копия 5: владелец проверяет свои машины (`find ~ -name 'btcbot_*.sql.gz'`, каталоги `artifacts/`), удаляет, записывает.
6. Копия 7: удалить сообщения или чат с ботом в Telegram владельца.
7. Контроль: `rclone ls <remote>:` показывает только `closure_deid_*` (и `closure_final_*`, если владелец записал основание и срок); `SHUTDOWN_LOG` содержит дату каждого удаления.

Что при этом теряется безвозвратно: возможность сопоставить голоса и тексты обратной связи с людьми. Научные результаты не затрагиваются: ни одна таблица результатов не ссылается на участников иначе как через `user_pk`, который после S6 равен NULL или удалён.

## 4. Разрешения, которые нужны для этого документа

- §2: закрытие платных ресурсов — П6 (после остановки VPS); off-site хранилище — отдельно, после переноса `closure_deid` и уничтожения или сознательного сохранения `closure_final`;
- §3.3 п. 3 и §3.5: удаление персональных данных и уничтожение копий — П4, в котором владелец либо подтверждает отсутствие оснований хранения (тогда полный архив уничтожается сразу после проверки обезличенного), либо записывает основание, срок и дату.
