## 2. Процедура прекращения платежей

1. Владелец заполняет недостающие поля таблицы §1 (провайдер VPS, облако для rclone, план GitHub, подписки) в приватной заметке вне git.
2. Порядок закрытия — обратный зависимости данных: сначала всё, что не хранит данные (5, 6, 7, 3-Actions), затем Telegram (4) после S7, затем VPS (1) после S8, последним — off-site хранилище (2) после переноса закрывающей копии на носители владельца.
3. Для каждого ресурса: выключить автопродление → экспортировать счета/историю платежей (для учёта) → отозвать ключи → удалить способ оплаты → закрыть аккаунт, если он нужен был только проекту.
4. Через 35 дней после закрытия — проверка выписок по карте: ни одного списания от ресурсов из §1.
5. Запись о выполнении — в `docs/closure/SHUTDOWN_LOG_<дата>.md` (без номеров счетов и сумм, только факт закрытия и дата).

## 3. Персональные данные участников

### 3.1. Что есть

По записям репозитория внешних пользователей у продукта не было (`docs/CURRENT_STATE.md:120`, `PROJECT_STATUS.md`; первая когорта `NOT_STARTED`; `access.preview_owner_only: true`). В базе могут быть строки владельца, тестовых аккаунтов и «известных контактов» (`docs/BETA_PREVIEW_V1.md:68-80` требует удалить тестовый аккаунт после проверки — проверить, сделано ли).

Где лежат персональные данные (`storage/beta_v0_schema.sql`, см. инвентарь):
- сырые идентификаторы Telegram: `beta_users` (`telegram_user_id`, `chat_id`, `tz`, `trader_type`, `brief_time`, `tier`, флаги push), `beta_allowlist`, `beta_waitlist`;
- связанные через `user_pk`: голоса `beta_feedback`, `beta_message_votes`; свободный текст `beta_feedback_messages`; причины `beta_reasons`; активность `beta_user_activity`; личные уровни `beta_price_alerts`; `beta_owner_forwards`; доставки `beta_notification_deliveries` (`telegram_message_id`, `error_summary`); `beta_market_alerts.target_user_pk`;
- псевдонимы: `beta_admin_audit` (HMAC-отпечатки с `BETA_FINGERPRINT_KEY`; старые строки — некейированный SHA-256, восстанавливаемый перебором), `beta_rejected_start_hashes` (HMAC с `BETA_TELEMETRY_SALT`), legacy `telegram_notification_deliveries.recipient_fingerprint` (некейированный SHA-256 chat id);
- вне базы: копии свободного текста участников в личном Telegram-чате владельца (`runtime/beta_bot.py:511-535`); все дампы базы (локальные 7, off-site 30/12/12) содержат персональные данные (`beta_v0_schema.sql:9-15`); **journald до 2026-09-28 мог содержать токен бота** (hotfix `53ccec14`; ротация токена после этого в записях не зафиксирована).

Обещания участникам (privacy notice v8, `beta/i18n.py:522-578`): хранение активности и текстов 120 дней; `/delete_me` удаляет всё; автоудаление через 30 дней после `/stop`; рыночные и прогнозные записи персональных данных не содержат. Purge-процедуры работают только внутри `--beta-notify-once` (`beta/delivery.py:307-319`): **после остановки таймеров автоматические удаления прекращаются**, поэтому закрытие должно выполнить их вручную.

### 3.2. Принцип

Закрытие не должно оставить участников в худшем положении, чем обещала privacy notice. Научная ценность продукта от персональных данных не зависит: ни одна таблица результатов (`beta_claims*`, `forecast_*`, `beta_forecasts`, `beta_episode_outcomes`, лента состояний, `beta_shadow_*`) не содержит идентификаторов пользователей. Поэтому по умолчанию персональные данные **удаляются**, а не архивируются.

### 3.3. Порядок (после S5 чек-листа, по отдельному разрешению, решение §6 п. 5)

1. **Инвентаризация:** `SELECT count(*), status FROM beta_users GROUP BY status; SELECT count(*) FROM beta_allowlist; ... beta_waitlist; ... beta_feedback_messages; ... beta_owner_forwards;` — записать счётчики (без идентификаторов) в `SHUTDOWN_LOG`.
2. **Уведомление:** если среди `ACTIVE` есть кто-то, кроме владельца и тестовых аккаунтов, — финальное сообщение (чек-лист S1) с указанием, что данные удаляются, и датой.
3. **Удаление в живой базе** (до финального дампа S4 или сразу после него — тогда повторить дамп): для каждого участника `delete_participant` (`storage/beta_v0_store.py:1207-1250`: каскад по `user_pk`, счётчик `beta_deleted_cohort_counts`, деидентификация аудита). Затем вручную: `beta_waitlist`, `beta_allowlist` целиком; `beta_invites.label` → NULL; `beta_notification_deliveries.error_summary` → NULL для строк с `user_pk IS NULL`; `telegram_notification_deliveries.recipient_fingerprint` → NULL; OUT-8 редакция аудита (`deploy/signalbot-beta-audit-deidentify.sql`, сначала `-count.sql` как dry-run); `beta_rejected_start_hashes` → удалить (счётчики `beta_rejected_start_counts` оставить).
4. **Обезличенный дамп:** после п. 3 снять `db_plain_deidentified.sql.gz` — именно он становится долгосрочным архивом и основой возможной публичной версии данных. Полный дамп с персональными данными (`$CB/pii/` и дампы, снятые до п. 3) — один зашифрованный экземпляр на срок, который назначит владелец (предложение: **30 дней**, по аналогии с обещанным сроком после `/stop`), затем удалить вместе со старыми off-site тирами `daily/weekly`, снятыми до удаления.
5. **Вне базы:** владелец удаляет пересланные тексты участников из своего Telegram-чата с ботом (или чат целиком); journald на VPS уничтожается вместе с VPS (экспорт журналов в `$CB` хранится зашифрованно вместе с `pii/`, так как может содержать старый токен; токен в любом случае отзывается в S7).
6. **Ключи псевдонимизации:** `BETA_FINGERPRINT_KEY`, `BETA_TELEMETRY_SALT` — уничтожить после п. 4 (без них отпечатки в аудите становятся невосстановимыми). До этого они нужны только для проверки восстановления.
7. **Запросы участников после закрытия:** контакт владельца остаётся; при запросе — подтверждение удаления по `beta_deleted_cohort_counts` и дате `SHUTDOWN_LOG`.

### 3.4. Что остаётся навсегда

Агрегаты без идентификаторов: `beta_deleted_cohort_counts`, `beta_rejected_start_counts`, даты действий в аудите (OUT-8), все рыночные и прогнозные таблицы, журнал заявок.
