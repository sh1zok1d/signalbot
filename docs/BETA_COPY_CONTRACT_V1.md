## 1. Три поверхности, один источник

| Поверхность | Когда | Окно | Что рендерит |
|---|---|---|---|
| `/catchup` | по запросу | 8ч по умолчанию, `/catchup <1–24>` | общий view (§3.1 решения), `kind = catchup` |
| Утренняя сводка | 08:00 (Киев), `/brief off` отключает | 00:00–08:00 | тот же view и тот же рендер, `kind = brief` |
| Push о необычном часе | только `TRIGGERED`-эпизод, прошедший гейт часа (§3.7) | скользящий 1ч вокруг эпизода | состояние 1ч, **не** имя детектора |

Общее правило: у этих трёх поверхностей нет своей логики. Если в одном и том же view текст отличается, это ошибка рендера, а не отдельный продуктовый выбор.

### 1.1 Каркас `/catchup` и утренней сводки

```
BTC за <окно> · <начало>–<конец> (Киев)
Цена <open> → <close> (<±%>), мин <low>, макс <high>
<Необычные часы окна: «Необычных часов не было.» или до 3 блоков>

Сейчас
1ч: <состояние или фактическая пара>
4ч: <состояние или фактическая пара>
24ч: <мин–макс, положение цены> · <OI к прошлым 24ч> · <средний Funding>

Данные на <время> (Киев)
```

- У окна `/catchup` (1–24ч) нет собственной базовой линии: строка цены — только факты, без «обычный/необычный».
- Сравнения разрешены только там, где база уже есть: 30-дневные ранги для 1ч/4ч, «к прошлым 24ч» для 24ч.
- **24ч — только контекст.** Ярлыка там не бывает никогда (§3.4).
- **Блок «Необычные часы» (продуктовое решение владельца, 2026-10-02).**
  - В блок попадают часы окна, которые **прошли квалификацию на доставку** по §3.7 решения: `TRIGGERED`-эпизод и необычный час.
  - Сюда входят и часы, push по которым был **подавлен тихими часами** (23:00–07:00, Киев) или **дневным лимитом** (2 за UTC-сутки).
  - Квалификация — свойство рынка, а не доставки: подавление меняет только то, был ли push, но не то, был ли час необычным.
  - Не больше 3 часов, по времени. Это не второе правило значимости: источник тот же, что у push.
  - Подавление общим cooldown и `/push off` здесь не решаются (§6).

### 1.2 Каркас push

```
BTC · необычный час
<начало>–<конец> (Киев)

<Состояние 1ч или фактическая пара>
Цена <±%> (<open> → <close>)
OI <±%> · Delta <±$>
[Ликвидации <стороны> <$> — топ-5% на <k> из 3 бирж]   ← подтверждающие цифры, только при «похоже на вынос …»
<2–3 метрики> — <оба|все три> в топ-5% часовых окон за 30 дней
Биржи: <k> из 3 в одну сторону

[кнопки как в текущем push: 1ч · 24ч · Полезно · Шум]
```

- **Лимит — 8 строк.** Считаются непустые строки текста, включая заголовок и строку времени. Строка ликвидаций входит в лимит, кнопки — нет.
- Строку «почему пришло» (топ-5%, согласие бирж) писать обязательно: это гейт §3.7, пересказанный словами.
  - Перечисляются только метрики, которые сами по себе прошли порог.
  - Слова «оба» / «все три» обязательны: каждая названная метрика отдельно в топ-5%, это не сумма и не общий балл (§2.2).
- В одном push может быть больше одной `TRIGGERED`-точки в том же часу, но пользователь видит одно сообщение о часе.

### 1.3 Канонические параметры доставки в тексте

- **Дневной лимит push — 2** за UTC-сутки (`max_new_pushes_per_utc_day: 2`, §3.8 решения). Любой текст, где упомянут лимит (`/start`, `/help`, `/terms`), говорит «не больше 2 в день».
- **Drift реализации, код не меняется в этом проходе:**
  - `beta/i18n.py:256` — «не больше 3 в день»;
  - `config/beta_v0.yaml:40` — `max_new_pushes_per_utc_day: 3`.
  - Оба исправляются при реализации §3.8 решения.
- **Тихие часы** — 23:00–07:00 (Киев). **Утренняя сводка** — 08:00 (Киев).
- **Пометка в сводке или `/catchup` о часе без push** — один раз, одной строкой, только для двух причин подавления, которые решены:
  - тихие часы: `Ночью с 23:00 до 07:00 бот не пишет, поэтому это только в сводке.`
  - дневной лимит: `Сообщения об этом часе не было: за сутки уже было 2.`

## 2. Состояние → текст

Ярлыки и пороги — строго из §3.1 решения. Колонка «текст» — то, что печатается после `1ч: ` / `4ч: ` (в push — с заглавной буквы).

| Ситуация | Текст | Что обязательно рядом |
|---|---|---|
| цена ↑, OI ↓, Delta + | `похоже на выход шортов` | цена %, OI %, Delta |
| цена ↑, OI ↑, Delta + | `похоже на рост с новыми лонгами` | то же |
| цена ↓, OI ↑, Delta − | `похоже на снижение с новыми шортами` | то же |
| цена ↓, OI ↓, Delta − | `похоже на выход лонгов` | то же |
| строка выше + пересекающийся эпизод `LIQUIDATION_STRESS_*` | `похоже на вынос лонгов` / `похоже на вынос шортов` | цена %, OI %, Delta; сырые цифры ликвидаций (сумма, сторона, k из 3 бирж) — как подтверждение |
| диапазон в нижнем хвосте, OI не в нижнем | `сжатие` | диапазон %, «в нижних 20% за 30 дней» |
| ничего из выше | `обычное состояние` | — |
| Delta против цены | фактическая пара: `рост при снижении OI`, `рост с ростом OI`, `снижение с ростом OI`, `снижение при снижении OI` | `Delta <±$> — против направления цены, без интерпретации` |
| по цене согласны меньше 2 из 3 бирж | `биржи расходятся` | изменение цены по каждой бирже |
| OI меньше чем с 2 бирж | фактическая пара цена + Delta | `OI н/д: сейчас есть с 1 из 3 бирж` |
| Delta нет | фактическая пара цена + OI | `Delta н/д — без неё не интерпретируем` |
| сжатие, но OI н/д | `сжатие, OI н/д` | диапазон % |
| ранги незрелые | `мало истории` | сырые цена/OI в процентах, «(N дн. из 30)» |
| данные отстают / неполные | `данные неполные` | время последних полных данных |

Если ни одна строка не подходит однозначно, выбирается самый фактический вариант: фактическая пара, а не ярлык.

**Префикс «похоже на» (продуктовое решение владельца, 2026-10-02).**
- Каждый причинный или механистический ярлык начинается с «похоже на», включая ярлыки выноса или ликвидационного сжатия (`похоже на вынос лонгов`). Это глобальное правило §3.1 решения («every inferred label is prefixed «похоже на»») применено и к строке «вынос», которая в словаре §3.5 записана без префикса.
- Сырые цифры ликвидаций (сумма, сторона, сколько бирж) можно показывать рядом как подтверждающие факты. Сами по себе они не ярлык.
- Без префикса пишутся только описательные состояния, которые не утверждают причину:
  - `сжатие`, `обычное состояние`, `биржи расходятся`, `мало истории`, `данные неполные`;
  - фактические пары (`рост при снижении OI` и т.п.).

### 2.1 Delta: единица и агрегирование (проверено по коду, без изменений кода)

| Уровень | Что считается | Где в коде |
|---|---|---|
| 1м бар, биржа | `taker_buy_volume` / `taker_sell_volume` — сумма `qty` сделок по стороне агрессора (`is_buyer_maker` → продажа) | `data_ingestion/bar_builder.py` (`Bar1m`) |
| 5м, биржа | `taker_delta_notional_usd = Σ notional(taker_buy) − Σ notional(taker_sell)` по 1м барам. Notional = `qty × close бара` для `base` или `qty × contract_multiplier × close` для `contracts`. Только если сплит есть на **каждом** баре и инструмент notional-eligible, иначе `None` | `analytics/feature_engine/exchange_features.py::_volume_taker_features`, `analytics/feature_engine/units.py::notional_usd_per_bar` |
| 5м, кросс-биржа (лента) | `taker_delta_notional_usd_sum = fsum` по **участвующим** биржам семейства `taker_flow`. Значение есть, только если участвует не меньше `min_venue_coverage` (2) бирж, иначе `None` | `analytics/feature_engine/consensus.py` (блок `taker_flow`); на ленту — `beta/state_tape.py::extract_metrics` как `c:taker_delta_notional_usd_sum` |
| 1ч / 24ч | Сумма 5м-значений `c:taker_delta_notional_usd_sum` по корзинам окна. Если хоть одна корзина или значение отсутствует — `None` (частичной суммы нет) | `beta/horizons.py::_sum_metric`, спецификация `"taker"` в `beta/horizons.py` |
| Рендер сейчас | `Delta: −$84 млн (продавцы)` через `fmt_usd` | `beta/formatter.py::_taker_text`, ключи `taker_line` / `taker_na` в `beta/i18n.py` |

**Вывод для копирайта:**
- **`$` допустим.** Величина — нотионал в долларах (по цене закрытия 1м бара USDT-перпа). Текущий прод-рендер уже печатает её с `$`.
- Показывать округлённо (`$84 млн`), без центов и без ложной точности: нотионал приблизительный, по close бара, а не по цене сделок.
- **Ограничение.** 5м-сумма идёт по 2 **или** 3 биржам, в зависимости от того, сколько участвовало в корзине. 1ч-сумма может смешивать корзины с разным числом бирж, а число участвовавших бирж горизонт сейчас не отдаёт.
- Поэтому текст **не должен утверждать «по 3 биржам»** про Delta. Раскрытие «по 2 из 3 бирж» — вопрос реализации view (§6), а не новое состояние.
- 4ч (§3.6 решения) — та же сумма 5м-значений по 48 корзинам.

### 2.2 «Топ-5%»: семантика перцентилей (проверено по коду, без изменений кода)

- **Что ранжируется.** Три метрики 1ч: `range_width_pct_median`, `price_move_pct_median`, `volume_notional_usd_sum` (`beta/context.py::CONTEXT_1H_METRICS`).
  - Каждая ранжируется **отдельно** замороженным percentile core (mid-rank) против значений скользящего 1ч, взятых на каждом 5м шаге за `[T − 30д, T)` (`beta/context.py::context_1h`).
  - Комбинированного балла нет.
- **Порог.** `context.label_high = 0.95` в `config/beta_v0.yaml`, сравнение `rank >= label_high` (`beta/context.py::level_label`). Уровень выдаётся только при `tier == "mature"`.
- **Как читать «диапазон и объём — оба в топ-5%».** Каждая из двух метрик **независимо** имеет ранг ≥ 0.95. Правило §3.7 решения: «не меньше двух из трёх метрик ≥ `label_high`» — это подсчёт независимых условий, не совместный порог.
  - Поэтому копирайт перечисляет только реально прошедшие метрики и пишет «оба» / «все три».
- **База — «часовые окна».** Это скользящие 1ч окна с шагом 5 минут, они перекрываются. Поэтому в тексте «топ-5% часовых окон за 30 дней», а не «топ-5% часов».
- **Блокер: знаковое движение цены.**
  - `price_move_pct_median` — знаковая величина (`(close − open) / open`), а конфиг прямо помечает `label_*` как пороги для «unsigned dims».
  - Буквально `rank(price_move) ≥ 0.95` = только **сильный рост**: сильное падение имеет ранг ≤ 0.05 и в гейт не засчитывается.
  - Решение не уточняет, задумано ли это. Копирайт этого не решает и новых порогов не вводит: до фиксации владельцем строка «цена — в топ-5%» допустима **только для роста**.
  - Для падения цена в списке прошедших метрик не упоминается (см. пример 3.3, где прошли диапазон и объём).

### 3.12 Ошибка аргумента `/catchup`

```
Окно — от 1 до 24 часов. Например: /catchup 4
```

### 3.13 Чего не бывает

- Push в 23:00–07:00 (Киев), третий push за UTC-сутки, push внутри общего cooldown, push за час, который не прошёл гейт. Пользователь в этих случаях **ничего не получает** в момент события.
- Часы, подавленные тихими часами или дневным лимитом, появляются в следующей сводке или `/catchup` (§1.1, пример 3.2). Подавленные cooldown — открытый вопрос (§6).
- Отдельное сообщение о 5м-событии.
- Сводка с текстом «рынок спокоен, можно…» или с любым продолжением, которое говорит, что делать или что будет.

## 4. Никогда не показывается пользователю

**Внутреннее (продуктовое решение владельца: никогда не видно пользователю ни на одной поверхности):**
- имена детекторов и правил (`PRICE_OI_CONTRACTION_UP`, `LIQUIDATION_STRESS_LONG`, `TAKER_FLOW_EXTREME`, `BETA_EVENT_RULES_V1`), включая их русские названия-события из текущего `push_title` («СОБЫТИЕ: …»);
- строка `push_id` целиком («Эпизод {pid} · правила {rules}»);
- id эпизодов, `episode_pk`, внутренние id пользователей и доставок;
- версии правил, контекста, горизонтов и схемы (`BETA_CONTEXT_1H_V2`, `BETA_HORIZON_TOD_V2` и т.п.), хеши и digest;
- состояния эпизодов (`TRIGGERED`, `ARMED`);
- причины подавления (`HOUR_NOT_UNUSUAL`, `QUIET_HOURS`, `GLOBAL_COOLDOWN`);
- `kind`, внутренние имена столбцов и метрик.

**Исследовательская лексика:**
- «baseline», «перцентиль 0.95», «ранг», «tier», «эпизод», «когорта», «детектор», «гипотеза», «OOS», «edge», «значимость», «p-value», «N», «консенсус», «площадка».
- Каноническое слово для Binance/Bybit/OKX — **«биржи»** (продуктовое решение владельца). «Площадки» в текущем каталоге — drift (§6).
- Вместо ранга пишется «топ-5% часовых окон за 30 дней» / «в нижних 20% за 30 дней».

**Прогноз и совет:**
- всё из `beta/i18n.py::_FORBIDDEN_RU` (`прогноз`, `вероятно`, `скорее всего`, `ожидается`, `сигнал`, `цель`, `разворот`, `продолжение`, `плечо`, `киты`, `закрытие шортов`, `лонг сейчас` и т.д.);
- в этих поверхностях также не используются, хотя фильтр их пока не ловит: «дальше», «скоро», «готовится», «уровень поддержки/сопротивления», «пробой», «ложный пробой», «давят», «вход», «шанс», «перекос в сторону», «бычий/медвежий», «лучше подождать».

**Хайп:**
- «срочно», «внимание», «обвал», «памп», «дамп», «мощный», «ракета»;
- восклицательные знаки, КАПС, эмодзи-сирены.

**Повторные дисклеймеры:** только в `/start` и `/terms`.

## 5. Правила product copy Signalbot (контракт для реализации)

1. **Факт → сравнение → интерпретация, именно в таком порядке.** У каждого числа есть единица и окно времени. Сравнение — только с базой, которая реально есть: 30 дней для 1ч/4ч, прошлые 24ч для 24ч. Для произвольного окна `/catchup` слов «обычно/необычно» нет.
2. **Любой причинный или механистический ярлык — только с «Похоже на …» и только при полном наборе.** Это касается и выноса: `похоже на вынос лонгов`. Нужны все три наблюдения — цена, OI и Delta, — и они согласованы по §3.1. Если хоть одного нет или одно противоречит, печатается фактическая пара и короткая причина. Сырые цифры ликвидаций можно показать рядом как подтверждение. Без префикса пишутся только описательные состояния: «сжатие», «обычное состояние», «биржи расходятся», «мало истории», «данные неполные» и фактические пары.
3. **Только прошлое и настоящее.** Ни слова о том, что будет, куда пойдёт цена и что делать. Сюда относится и косвенное: «рынок готовится», «давление растёт», «лучше подождать». Каждый шаблон проходит `assert_descriptive` и списки §4.
4. **Незнание называется, а не прячется.** Пишется `н/д`, `мало истории (N дн. из 30)`, `биржи расходятся` с цифрами по биржам, `данные неполные` со временем. Причина — не длиннее 8 слов. Нельзя молча подставлять соседние окна, биржи или старые значения.
5. **Никакой внутренней кухни.** Пользователь не видит имён детекторов, `push_id`, id эпизодов, версий правил, хешей, состояний эпизодов и исследовательской или внутренней лексики (§4). Push описывает час, а не 5м-событие.
6. **Одно слово — одно понятие на всех поверхностях.** Используются OI, Delta, Funding, «биржи» (никогда «площадки»), «диапазон», «объём», а ярлыки — дословно из §3.1 решения, без синонимов и вариаций. Если термин нужно объяснять, объяснение живёт в `/terms`, а не в сообщении.
7. **Время всегда по Киеву и всегда интервалом.** Пишется `13:05–14:05 (Киев)`, а не «за последний час». `/catchup` и сводка заканчиваются строкой `Данные на …`.
8. **Коротко и на один экран телефона.** Push — не больше 8 непустых строк текста, включая заголовок и время, без кнопок; сводка и `/catchup` — не больше 15. Без восклицательных знаков, КАПСа, хайп-слов и эмодзи-сирен. Дисклеймер — только в `/start` и `/terms`.
9. **Молчание — нормальное состояние.** Подавленный push не порождает текста. Нельзя «добивать» пользователя заменой — ни тизером, ни сообщением «было бы интересно». Час, подавленный тихими часами или дневным лимитом (2), попадает в следующую сводку или `/catchup`. Там один раз допустима короткая пометка из §1.3, почему push не было.
10. **Одинаковый формат чисел.**
    - Десятичная запятая; пробел между тысячами; знак всегда (`+`, `−` U+2212).
    - Цена — в целых долларах. Изменение цены — 2 знака после запятой, OI — 1 знак.
    - Суммы — `$84 млн` (Delta и ликвидации — USD-нотионал, §2.1), кратность — `2,4×`.
    - «Топ-5%» — всегда с базой и словом «оба» / «все три», если метрик несколько (§2.2).
    - Всё это через существующие `fmt_*` в `beta/i18n.py`.

## 6. Решено в финализирующем проходе, drift и оставшиеся блокеры

**Решено владельцем 2026-10-02 (зафиксировано выше):**
- блок «Необычные часы» включает часы, подавленные тихими часами или дневным лимитом (§1.1);
- «похоже на» у всех причинных ярлыков, включая вынос (§2);
- лимит push — 2 в день (§1.3);
- слово «биржи» (§4, правило 6);
- внутренние имена и id никогда не видны (§4);
- push — 8 строк (§1.2, правило 8).

**Drift реализации (код не менялся, исправляется при реализации):**
- лимит «3 в день»: `beta/i18n.py:256` и `config/beta_v0.yaml:40` против 2 по §3.8 решения;
- «площадок / площадках»: `beta/i18n.py:460`, `:499`, `:505`, `:525`, `:531`, `:557`, `:728`;
- текущий push показывает внутренности: `push_title` («СОБЫТИЕ: {name}») и `push_id` («Эпизод {pid} · правила {rules}») — уходят по §3.9 решения.

**Оставшиеся блокеры и открытые вопросы:**
- **Решение не смержено.** `PRODUCT_FIRST_DECISION_V1.md` есть только в `ccr-f8122eff-axgnoe`. До мержа этот контракт не каноничен.
- **Знак движения цены в гейте (§2.2).**
  - Буквально «цена ≥ `label_high`» = только сильный рост, а сильное падение в гейт не засчитывается.
  - Нужно решение владельца: так задумано, или нужен симметричный критерий? Второй вариант — изменение правила гейта в решении, а не в копирайте.
  - До этого цена в строке «почему пришло» упоминается только для роста.
- **Число бирж в Delta и объёме.** Кросс-биржевые суммы Delta и объёма идут по 2 или 3 участвующим биржам, а горизонт не отдаёт, сколько их было.
  - Нужно решить при реализации view, раскрывать ли «по 2 из 3 бирж».
  - До этого текст не утверждает «по 3 биржам» для сумм.
- **Подавление общим cooldown и `/push off`.** Не решено, попадают ли такие часы в блок «Необычные часы». По логике «квалификация — свойство рынка» — да, но это не зафиксировано владельцем.
- **«Сжатие» — нижний хвост.** Пример 3.10 читает «нижний хвост» как ранг ≤ 0.20 (полосы §3.1). Точная граница фиксируется в решении, не здесь.
- **Тихие часы и UTC-сутки.** Лимит считается по UTC, тихие часы — по Киеву. Пользователь видит только киевское время, расхождение границ суток в тексте не объясняется.
